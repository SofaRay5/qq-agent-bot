## Context

用户在做一个练手项目（`qq-agent-bot`），目标不是"最快把代码跑起来"，而是**自己练习工程设计能力**。
项目的 `CLAUDE.md` 和 `docs/里程碑Checklist.md` 明确把里程碑 1 的核心任务标为 🧠（用户必须自己
设计/编写），Codex 的角色限定在 review、答疑、补测试骨架。

因此这份计划**不是"我帮你设计好 Pydantic 模型该长什么样"**，而是一个**分步骤的自学+自建流程**：
每一步做什么、产出什么、什么时候该来找我 review，边界清楚，不替用户做设计决策。

## 里程碑 1 的验收标准（复用 checklist 原文，作为最终目标）

- 能用自己写的 Pydantic 模型成功解析：群消息、私聊消息、心跳事件三种示例 JSON
- 故意构造缺字段的错误 JSON，模型正确抛出验证错误（不是静默出错）
- 单元测试覆盖：群消息解析 / 私聊消息解析 / 未知 post_type 容错
- 能脱稿讲清楚 `message_type` 和 `sub_type` 的区别

## 分步执行顺序

### 第 1 步：读协议文档（🧠 独立完成，无需 Codex 参与）
- 通读 OneBot v11 官方文档的事件部分：https://github.com/botuniverse/onebot-11
- 重点看：`post_type` 有哪几种取值（message / notice / request / meta_event）、
  每种取值下 `sub_type` 又细分成什么
- 项目自带的 `docs/QQ机器人工程化设计文档.md` 的 "02. OneBot 适配层设计" 一节里有
  精简版的事件 JSON 示例，可以对照官方文档快速定位关键字段，但不要只看这个精简版就
  开始写代码——官方文档里字段更全，尤其是 `notice`/`request` 类事件

### 第 2 步：画事件类型层级图（🧠 独立完成，纸上或工具画都行）
- 画一张 `post_type → sub_type` 的分类关系图
- 目的：写代码前先在脑子里理清"消息事件、通知事件、请求事件、元事件"分别包含哪些子类型，
  避免写模型时漏掉分支
- 不需要拿给 Codex 看这张图本身（手画的图我也看不到），但下一步写代码骨架时如果对某个
  分类关系不确定，可以来问

### 第 3 步：做两个关键设计决策（🧠 独立完成，建议写下理由，哪怕几句话）
1. **`message` 字段用数组格式还是 CQ 码字符串格式？**
   设计文档里提到 NapCat 配置可以选 `messagePostFormat: "array"`，需要你自己决定模型
   只支持数组格式，还是两种都要兼容，并想清楚为什么
2. **"条件必填"怎么实现？**
   `message_type="group"` 时 `group_id` 必填，`private` 时应为 `None`——想清楚用
   Pydantic 的 `model_validator` 怎么写这个校验逻辑（不要求现在就写代码，想清楚思路即可）

这两条决定了 `event.py` 模型骨架的基本形状，建议想清楚了再动手写代码，避免写到一半推倒重来。

### 第 4 步：手写 `onebot_adapter/event.py` 第一版骨架（🧠 独立完成）
- 哪怕写得丑、不完整都没关系，先有一版
- 三种事件（群消息、私聊消息、心跳）至少要能覆盖
- 写完之后来找 Codex review——这是第一个"叫我"的节点

### 第 5 步：Codex Review 模型骨架（🤖 Codex 协助）
Codex 会做的事：
- 对照 OneBot v11 官方文档，检查模型有没有漏掉字段
- 检查 `model_validator` 的条件必填逻辑是否正确覆盖了 group/private 两种分支
- 提出问题引导用户发现问题，而不是直接改代码替用户做决定（除非用户明确要求直接改）

### 第 6 步：补单元测试骨架（🤖 Codex 协助生成骨架，🧠 用户检查是否真覆盖了关心的场景）
- Codex 可以生成 `tests/test_onebot_event.py` 的测试函数骨架 + 示例 JSON fixture
- 用户需要自己检查：这些测试是不是真的覆盖了自己关心的边界情况（比如缺字段、
  未知 post_type 容错），不是简单地"测试能跑就行"

### 第 7 步：跑通验收标准
- 三种示例 JSON（群消息/私聊消息/心跳）能被正确解析
- 构造一个缺字段的错误 JSON，确认模型抛出验证错误而不是静默失败或崩溃
- `uv run pytest` / `uv run pre-commit run --all-files` 全部通过
- 走一遍 `docs/DEV_WORKFLOW.md` 里的流程，commit + push

### 第 8 步：口头自测（🧠 独立完成）
- 能不能脱稿讲清楚 `message_type` 和 `sub_type` 的区别——这是验收标准之一，
  建议自己对着代码复述一遍，讲不清楚说明理解还不够扎实，回去补一下
