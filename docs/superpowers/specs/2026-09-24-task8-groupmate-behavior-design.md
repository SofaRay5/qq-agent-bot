# Task 8 群友行为、人格与费用设计

日期：2026-09-24

状态：用户已批准（2026-09-24）

## 目标与边界

把现有单轮 DeepSeek QQ 机器人扩展成“小薯”：群内经过明确触发后可以持续交谈，能够根据结构化角色卡保持口吻，在有限额度内选择回复或沉默，并保证不同私聊和群聊之间不会串话。

Task 7 的真实 NapCat 与视觉模型验收暂缓，Task 8 完成后一起测试。Task 8 继续使用当前 OneBot v11 正向 WebSocket、DeepSeek 和可选视觉模型，不实现长期记忆、浏览器后台、工具调用或服务器部署。

第一版使用普通 Python 内存状态机。近期上下文集中保存在协调组件内部，Task 10 可将其替换为 SQLite；只有未来出现复杂流程分支、checkpoint 或多 Agent 时才考虑迁移到 LangGraph。本任务不提前建立多套存储接口或空框架。

## 总体架构

消息处理流程：

```text
NapCat 事件
  → OneBot 消息提取
  → Dispatcher 去重与发送
  → GroupmateCoordinator 判断触发、窗口、冷却和额度
  → GroupmateReply 组合安全规则、角色卡和近期上下文
  → DeepSeek 返回回复或沉默
  → Dispatcher 按会话顺序发送
```

### `onebot_adapter/`

从数组消息段中提取文字、第一张普通图片、@、回复目标和发送者资料。适配层分别提供完整消息内容和“群内 @ 之后内容”，由核心层根据明确触发或持续窗口选择，确保持续窗口中的普通图片不要求再次 @。发送 action 后返回 NapCat 提供的机器人消息 ID，供核心层识别“回复小薯”的触发。适配层不包含人格、额度或 LLM 判断。

### `core/dispatcher.py`

继续负责事件入口、机器人自身消息过滤、消息 ID 去重、后台任务、OneBot 发送和发送失败隔离。它把合格消息交给群友协调组件，不承担会话状态和 prompt 组织。

### `core/groupmate.py`

`GroupmateCoordinator` 保存每个会话的内存状态，管理触发类型、持续窗口、近期上下文、模型尝试、实际回复、冷却、发送延迟和同一会话的处理顺序。状态字典只存在于该组件内部，避免状态散落到 Dispatcher 或 Agent。

### `agent/groupmate.py`

`GroupmateReply` 接受与 OneBot 无关的纯数据，加载已校验角色卡，构造模型消息并解析“回复或沉默”的 JSON 结果。它不导入 `onebot_adapter`。

### `core/budget.py`

用标准库 SQLite 原子保留本地每日调用计数。它不保存聊天正文、角色卡、图片、URL 或密钥。

## 触发规则

### 明确触发

以下消息一定成为模型候选：

- 任意非空私聊消息。
- 群内 @ 机器人。
- OneBot `reply` 段指向机器人近期成功发送的消息 ID。
- 去除开头空白后以角色卡名字“小薯”开头的群消息。

名字只匹配开头，避免普通句子中偶然出现“小薯”导致触发。群内 @ 仍只使用 @ 之后的文字和图片；回复与叫名字使用整条可见文字。图片继续遵守 Task 7 的“每条消息只处理第一张普通图片”规则。

机器人成功发送后，每个群只保留最近 100 个机器人消息 ID。没有返回消息 ID 或已被淘汰的旧 ID 不作为“回复小薯”触发。

### 持续对话窗口

群聊明确触发后开启该群的窗口：

- 默认持续 600 秒。
- 默认最多 5 次模型尝试和 5 次实际回复。
- 窗口内后续非机器人消息先加入近期上下文，再经过冷却和每日额度检查。
- 通过本地检查后调用模型，由模型选择回复或沉默。
- 调用失败和模型沉默都消耗一次窗口尝试；只有成功发送文字才增加回复数。
- 到期或任一窗口次数耗尽后，普通消息不再调用模型。
- 新的明确触发开启一个新窗口并重置窗口计数，但不能绕过每日总额度。

不活跃群聊不会持续积累聊天正文。新窗口从明确触发消息开始建立上下文。窗口结束后旧上下文可以删除；Task 10 再处理跨窗口长期记忆。

### 私聊

每条私聊都视为明确触发。近期上下文按 QQ 用户隔离，在进程运行期间保留；重启后清空。私聊不使用群聊持续窗口次数，但仍受每日总额度、上下文长度和发送节奏限制。

## 近期上下文与顺序

会话键采用私聊用户或群号，不同私聊、不同群之间完全隔离。群聊记录发送者昵称、QQ 号、消息顺序和机器人回复；昵称只作为不可信显示标签。

每个会话默认最多保留 20 条消息，并同时限制总字符数。超出任一上限时从最早消息开始删除。图片仅把当次视觉模型生成的短描述加入上下文，不保存图片字节或 URL。

每个会话有独立异步锁。同一会话按接收顺序完成判断、模型调用、延迟和发送，避免较早请求晚到后打断新话题；不同会话可以并发。关闭程序时取消并等待仍在运行的任务。

## 角色卡

仓库提供 `config/persona.example.json`。本机可创建 Git 忽略的 `config/persona.json`；实际文件存在时使用实际文件，否则读取示例。示例只提供“小薯”的名字和空白可编辑字段，不替用户设计具体人格。

核心字段参考 Character Card V2：

```json
{
  "name": "小薯",
  "description": "",
  "personality": "",
  "scenario": "",
  "speech_style": "",
  "identity_response": "",
  "example_dialogues": []
}
```

`name` 必须为 1–32 个字符。`description`、`personality` 和 `scenario` 各最多 2000 个字符；`speech_style` 和 `identity_response` 各最多 1000 个字符，这些字段允许暂时为空。`example_dialogues` 最多 3 组；存在的示例必须同时包含 1–1000 个字符的 `user` 与 `assistant`。整张角色卡最多 8000 个字符。配置错误必须在连接 NapCat 前指出字段路径并停止启动。普通 QQ 消息没有修改角色卡的入口；Task 9 再提供只有所有者能访问的编辑页面。

## 模型输入和安全边界

模型输入按固定层级组织：

1. 程序内置安全规则。
2. 经过校验的角色卡。
3. 当前会话的有限近期记录。
4. 当前用户消息或图片描述。
5. 严格输出格式要求。

安全规则和角色卡进入 system 消息；历史继续使用独立的 Human/AI 消息。用户正文、昵称、图片描述及未来记忆明确作为可能有误的资料，不获得修改角色卡、配置、额度、安全规则或执行管理操作的权限。

密钥、私有文件路径和后台设置不进入模型输入。消息长度、上下文上限、并发顺序和调用额度均由程序强制执行。Task 8 不提供工具调用或系统命令能力。提示词隔离只能降低人格劫持概率，不宣称完全消除提示词攻击。

## 回复或沉默协议

DeepSeek 必须返回以下一种 JSON：

```json
{"action": "reply", "text": "回复内容"}
```

```json
{"action": "silent", "text": ""}
```

程序使用标准库 `json` 解析，检查 action、文字类型、非空条件和 1000 字符的回复上限，不为修复格式再次调用模型：

- 明确触发时，超时、网络错误、空回复或格式错误发送一次固定失败提示。
- 持续对话和主动参与时，相同错误保持沉默。
- `silent` 消耗一次模型尝试但不增加实际回复数。

聊天和视觉模型都关闭 SDK 自动重试，使一次本地计数对应一次真实服务商 HTTP 尝试。

## 主动参与

主动参与仅用于没有明确触发、也不在持续窗口内的群消息，默认关闭。配置支持：

- `off`：不主动参与。
- `random`：先按本地概率抽样，通过后调用模型；模型仍可沉默。
- `topic`：冷却结束后调用模型，由模型根据话题决定回复或沉默。
- `both`：先随机抽样，再由模型判断话题，减少调用并保持相关性。

冷却期或额度不足时不调用模型。主动参与达到每日子额度后直接沉默，不发送额度提示。

## 统一额度

SQLite 按本地日期保存 `total`、`proactive` 和 `vision` 三个计数。每次提供商调用前用原子事务检查并增加对应计数：

- 默认全部模型调用每天最多 50 次。
- 主动参与调用每天最多 5 次。
- 视觉模型调用每天最多 5 次。
- 模型失败和模型沉默计数。
- 图片下载在视觉调用前失败时不计数。
- 一次成功图片回复通常分别消耗一次视觉调用和一次聊天调用。

视觉调用增加 `total` 与 `vision`；主动聊天增加 `total` 与 `proactive`；其他聊天只增加 `total`。进程重启不能恢复当天额度。额度数据库不可用时采用失败关闭策略，不进行无法计量的模型请求。

达到总额度后，主动候选保持沉默，明确触发回复“今天的聊天额度用完了，明天再聊吧”。达到视觉子额度时，图片明确触发回复“今天暂时不能识图了”。

## 回复节奏和配置

仓库提供 `config/settings.example.json`，本机可用 Git 忽略的 `config/settings.json` 完整覆盖。第一版字段和默认值：

```json
{
  "continuous_window_seconds": 600,
  "window_max_attempts": 5,
  "window_max_replies": 5,
  "daily_model_calls": 50,
  "daily_proactive_calls": 5,
  "daily_vision_calls": 5,
  "proactive_mode": "off",
  "proactive_probability": 0.05,
  "minimum_reply_interval_seconds": 8,
  "send_delay_seconds": 1.5,
  "context_max_messages": 20,
  "context_max_characters": 6000
}
```

配置边界如下：窗口 60–3600 秒；窗口尝试和回复各 1–20 且回复数不能超过尝试数；每日总调用 1–1000；主动与视觉子额度各 0–每日总额度；主动概率 0–1；最短间隔与发送延迟各 0–300 秒；上下文消息 1–100 条、总字符 500–20000。布尔值不能冒充整数，未知字段视为配置错误。Task 9 直接编辑同一格式，不建立第二套配置来源。

明确触发不会因最短回复间隔被丢弃，而是等待到允许发送；持续窗口和主动候选在冷却期直接跳过，不调用模型。生成成功后等待 `send_delay_seconds` 再发送。等待位于会话锁内，保证同一会话顺序。

## 失败处理和日志

- 配置错误在 NapCat 连接前失败。
- 额度数据库错误阻止新的模型调用；明确触发收到固定失败提示，普通候选沉默。
- 模型失败按明确触发与普通候选分别降级为固定提示或沉默。
- OneBot 发送失败不自动重发，避免重复消息。
- 单个会话失败不终止连接，也不影响其他会话或后续消息。
- 日志只记录错误类别、会话类型和排查所需的非正文标识，不记录聊天正文、角色卡正文、图片 URL 或密钥。

## 自动化验证

测试使用假时钟、假随机数、假模型和假 NapCat，不访问真实 QQ 或付费模型，覆盖：

- @、回复机器人消息、开头叫“小薯”和未触发消息。
- 持续窗口开始、重开、到期和次数耗尽。
- 私聊、不同群之间的上下文隔离。
- 上下文条数与字符限制。
- 冷却、发送延迟和同一会话处理顺序。
- 回复与沉默 JSON 的合法、非法和失败路径。
- 主动参与默认关闭，以及 random、topic、both。
- 总额度、主动额度和视觉额度的并发原子限制与重启保留。
- 角色卡与设置校验，以及用户消息不能改变本地配置。
- Task 7 图片路径继续工作并分别计算视觉、聊天调用。
- 任一消息失败后，下一条普通消息仍可处理。

Task 8 自动化检查完成后，按照测试指南在真实 NapCat 上把 Task 7 识图和 Task 8 群友行为一起验收，再分别更新最终验收勾选。
