# pre-commit 四个检查项分别查什么（个人笔记）

> 这不是正式规范文档，是解释性笔记，帮助理解 `.pre-commit-config.yaml` 里配的每个钩子
> 在查什么、为什么会拦下 commit。

## 总览

每次 `git commit`，pre-commit 会依次跑这四项，任何一项失败都会拦下这次提交：

| 钩子 | 类别 | 查什么 |
|---|---|---|
| `ruff` | 代码检查（lint） | 找出明显的代码问题：没用到的 import、未定义变量、危险写法 |
| `ruff-format` | 代码格式化 | 统一缩进、引号、空行等排版，跟内容对不对无关 |
| `mypy` | 类型检查 | 检查类型标注是否自洽，能不能提前发现类型不匹配的 bug |
| `pytest` | 功能测试 | 实际运行测试代码，检查程序行为是否符合预期 |

四者的分工：**ruff 管"写得规不规范"，mypy 管"类型对不对"，pytest 管"跑起来对不对"**——
三个维度互不重叠，一个都不能替代另一个。

## ruff：查什么

Lint 部分（`[tool.ruff.lint] select = ["E", "F", "I", "UP", "B"]`）：

| 规则代码 | 全称 | 查什么 | 例子 |
|---|---|---|---|
| `E` | pycodestyle errors | PEP8 风格问题 | 行太长、缩进不对、多余空格 |
| `F` | pyflakes | 明显的逻辑错误 | 导入了但没用的模块、用了没定义的变量、重复定义函数 |
| `I` | isort | import 顺序 | 标准库/第三方库/本地模块的 import 要不要分组排序 |
| `UP` | pyupgrade | 过时写法 | 用了 Python 老版本的写法，提示换成新版本更简洁的等价写法（比如类型标注用 `str \| None` 而不是 `Optional[str]`） |
| `B` | flake8-bugbear | 容易踩坑的写法 | 可变默认参数（`def f(x=[])`）、循环变量在闭包里被延迟绑定这类经典陷阱 |

`ruff-format` 部分是另一件事：单纯格式化，不判断对错，只是把代码排版成统一风格（类似
自动帮你重新缩进、统一引号），跟 lint 的"找问题"是分开的两个动作。

## mypy：查什么

**类型是否自洽**，运行代码之前，纯靠读代码里的类型标注做静态分析。典型能抓到的问题：

- 函数声明返回 `str`，但某个分支实际 `return None`
- 把一个可能是 `None` 的值直接当非 `None` 用（比如 `group_id.strip()`，但 `group_id`
  类型是 `str | None`）
- 调用函数时传错了参数类型
- 没写类型标注的函数（因为项目开了 `strict = true`，这个本身就是错误——你之前 `main.py`
  被拦下就是这个原因）

它不运行代码，纯粹是"读代码、推类型、看逻辑通不通"，所以速度快，但也只能抓类型层面的
问题，抓不到"这个函数算出来的结果对不对"这种语义错误——那是 pytest 的职责。

## pytest 是什么

Python 最常用的测试框架。写一批 `test_*.py` 文件，里面是一堆 `def test_xxx():` 函数，
每个函数断言（`assert`）某段代码在给定输入下产出了预期结果。跑 `pytest` 命令会自动发现
所有这些函数、逐个执行、汇总"通过/失败"的结果。

它替代的是"手动跑一遍程序、肉眼看输出对不对"这种验证方式——测试写好之后，以后改代码
只要重跑一遍 pytest，几秒钟内就知道有没有把之前跑通的功能改坏（这叫"回归测试"）。

## 在这个项目里，pytest 具体测什么

对照设计文档 `05. 项目结构` 里的测试策略表，分四类：

| 测试类型 | 测什么 | 例子 |
|---|---|---|
| 单元测试 | 单个函数/类的行为，不依赖外部系统 | `make_thread_id()` 给定 group_id/user_id，返回的字符串格式对不对 |
| 单元测试 | 消息段编解码 | OneBot 数组格式的 JSON 转成 `UnifiedMessage` 之后，字段对不对 |
| 单元测试 | 数据库存取 | `UserProfileStore.upsert()` 写进去之后 `load()` 能读出同样的数据 |
| 集成测试 | 多个模块拼起来是否正常工作 | Agent + Checkpointer：连续问两轮，第二轮能不能记住第一轮说的话 |
| 协议契约测试 | 外部输入（不可信数据）解析是否符合预期 | 构造一份标准 OneBot 群消息 JSON，断言 Pydantic 模型解析出来的字段完全匹配；再构造一份缺字段的 JSON，断言会抛出验证错误而不是静默出错 |
| 手动验收 | 真实环境下的端到端行为 | 真实 QQ 群里 @机器人，看它是否正确回复——这类没法自动化，靠人工走一遍 checklist 里的验收标准 |

## 为什么 pre-commit 里配了 pytest 钩子

每次 commit 前自动跑一遍已有测试，防止"改了 A 模块，把 B 模块跑坏了但没发现"这种情况在
你自己都没意识到的时候就被提交进 git 历史。

## 现在为什么会失败

`tests/` 目录还是空的，pytest 找不到任何 `test_*.py` 文件，默认行为是把"零测试"当成异常
情况报错（退出码 5），不是"通过"。等 milestone 1 你写 `onebot_adapter/event.py` 的协议
契约测试（checklist 里明确要求了：群消息/私聊消息/未知 post_type 容错），这里就会自然
有内容、pytest 钩子也会正常跑通。

## 一个最简单的测试长什么样（示例，仅供参考格式）

```python
# tests/test_session.py
from core.session import make_thread_id

def test_group_thread_id():
    assert make_thread_id("group", "111", "222") == "group:222:user:111"

def test_private_thread_id():
    assert make_thread_id("private", "111", None) == "private:111"
```

一个测试函数只断言一件事，函数名要说清楚测的是什么场景（这样测试失败时，光看函数名就
知道哪个场景挂了，不用打开代码去猜）。
